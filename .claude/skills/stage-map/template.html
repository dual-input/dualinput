The bench

The bench runs real cores on this PC and drives them from outside, as a sim and a network would. After each scenario it replays every core's recording, and fails if a replay differs from its run. It needs no sim and no second PC.

node tools/bench.tsBuilds the bench build of the core, runs each scenario, and replays every recording.
node tools/bench.ts loadRuns one core under an hour of a busy flight, then reports the loop against its budgets.
log.txtEvery core, release builds included, logs its loop's stats once a minute.

bench only

What The bench's socket is a TCP port on 127.0.0.1 that only the bench build opens. The bench sends it JSON lines, and the core's first line answers with its version and hash.

Why The bench may reach the core only where a pilot's sim and network do, so every scenario runs a pilot's code.

The test units

bench only

What The test units are two units only the bench build registers. The lines unit counts the bench's numbered lines and exits on request, and the load unit does a busy session's work.

Why The loop and its recording need a workload to measure before the real features exist.

How

The lines unit

  • count n: logs n and puts out Counted(n)
  • exit: puts out the core's exit

The load unit

  • a flight-model input: 100 outputs, then holds the loop 98.7µs, as 100 write functions did in p10
  • every 60s: holds the loop 100ms, as a write function at its limit
  • a timer 5 times a second, and a file job every 30s
  • any other input: passes its bytes on as an output
  1. The lines unit parses each line from the socket.apps/core/src/bench/lines.rs:26fn line · serde_json::from_slice
  2. For a count line, it logs n and puts out Counted(n).lines.rs:31–32tracing::debug!(n, …) · cx.out(Counted(n))
  3. For an exit line, it puts out the core's exit.lines.rs:34ToCore::Exit => cx.out(Exit)
  4. The load unit reads each input's kind from its first two bytes.apps/core/src/bench/load.rs:90fn input · match kind
  5. The start input sets its timers and its file job going.load.rs:98START => cx.timer(TICK, …) · cx.timer(STOP_EVERY, …) · cx.job(…)
  6. For a flight-model input, it puts out 100 writes, then holds the loop.load.rs:105–114cx.out(Wrote::Entry { … }) · hold(started, WRITE_FUNCTIONS)
  7. Once a minute, its stop timer holds the loop for 100ms.load.rs:145–146fn stop · hold(Instant::now(), LIMIT)
  8. A hold spins until its time is up. Nothing the unit puts out depends on how long it spun, so the replay still matches.load.rs:168–170while started.elapsed() < long { spin_loop() }
  9. The end input puts out the core's exit.load.rs:134END => cx.out(Exit)

The playback

bench only

What The playback feeds the core a recorded 10-minute flight at its real pace, plus a session's made-up inputs. You run it by hand with node tools/bench.ts load, and stage 14 runs it again with real write functions.

Why Every input goes through one loop, so a loop that falls behind a busy flight makes every pilot's action wait. The playback lets the bench check the loop keeps up before the features that bring that load exist.

How
  1. A load line from the bench starts the playback on a thread of its own.apps/core/src/bench/playback.rs:26pub fn play(path, plays, queue, source, context)
  2. It decompresses the capture into memory and indexes its records.playback.rs:59–61Capture::read · zstd::stream::read::Decoder
  3. It sets up the made-up streams: 109 cockpit changes a second, 30 avatar poses, 1 heartbeat, 10 panel messages, 50 ATC frames, and cursor drags.playback.rs:189fn session() -> Vec<Box<dyn Stream>>
  4. It keeps every stream in a heap, ordered by when its next input is due.playback.rs:227BinaryHeap<Reverse<(u64, usize)>>
  5. It sleeps until the next input is due, then pushes it into the queue. Inputs due together, such as a burst of traffic records, go in back to back.playback.rs:240, 243thread::sleep(…) · queue.push(source, bytes, true)
  6. It pushes a start input first and an end input last, which the load unit starts and exits on.playback.rs:233, 249input(START, &[]) · input(END, &[])

The killed-core scenario

bench only

What The killed-core scenario sends a core 300 numbered lines, kills it, and counts the lines its recording kept.

Why The core's budget says a crash loses at most the recording's last second, and this scenario checks it.

How
  1. The scenario starts a core in a run folder of its own.tools/bench/scenarios/killed-core.ts:20–21new BenchRun("killed-core", t) · run.core("a")
  2. It sends 300 numbered lines, one every 15.6ms or so, the step of Windows' timer.killed-core.ts:24–27core.send({ kind: "count", n }) · sleep(10)
  3. It kills the core.killed-core.ts:30core.kill()

The stand-in sim

bench onlywired in stage 4

What The stand-in sim plays MSFS for the bench. It tracks a process the bench names as the sim's, takes connections, and loses one or quits on request.

Why Stage 4 builds the core's connection to the sim, and the bench has to test it without MSFS running.

How

No sim

  • An open fails with E_FAIL, as during the sim's boot.
  • Looking for the sim finds nothing until the bench names a process.
the bench names a process, the core looks

Sim running

  • An open succeeds, then MSFS's open message follows.
  • The bench can make it lose a connection.
the bench asks it to quit

Sim quit

  • The quit message went to every open connection.
  • An open still succeeds, then nothing answers.
the process ends

Sim exited

  • It reports the process's exit code.
  • It keeps watching a process the bench named next.
the core looks again
