    A package in a group that the sim's report lists after PANEL_PATCH, such as CUSTOM_INSTRUMENT, would mount after FS Copilot's, and YourControls' package, with no hint, sits in the unset group, which mounts before UI_PATCH and PANEL_PATCH (read; not run).

    FlightSimulator2024.exe's file version, 1,9,18,0, and the sim's reports' BuildVersion="1.9.18.0" do carry the release (read).

F4. fspackagetool runs the sim to build, so no GitHub-hosted runner can run it (read in its binary; Q3).
    Everything we ship that is a Copy-only package (files plus our own manifest.json and layout.json) needs no fspackagetool, and the sim ran such packages (measured 2026-10-08 and 2026-10-09).
    The figure's SimObject is the exception: fspackagetool rewrites its model (Q3).

F5. Older SDK Core installers stay downloadable at a predictable URL, though the listing links only the newest two (measured; Q4).
    So a script can pin an SDK version, which cargo-msfs itself can't: it always takes the listing's first entry.

F6. cargo-msfs's "update" likely never sees itself up to date on this machine, because the SDK's own version.txt overwrites cargo-msfs's (read in source; unverified by a run; Q4).

Q1. MOUNT ORDER FOR TWO PACKAGES THAT BOTH HOLD html_ui/Pages/VCockpit/Core/VCockpit.js
======================================================================

The documented rules (Virtual File System Information, https://docs.flightsimulator.com/msfs2024/html/2_DevMode/Menus/Tools/Virtual_File_System_Information.htm, read 2026-10-18):
- Content.xml of each package source decides only which packages are enabled.
- The same package name in two sources: only the copy from the source with the highest score activates (Developer Mode infinite, boot-required 100, Community2024 4, Community 3, Marketplace installed 2, Marketplace streamed 1, Streamed 0, base -1).
- Different packages holding the same path: packages mount in the order their Package Order Hint gives; within one hint they mount alphabetically; a package mounted later takes priority over earlier ones, so by default a Z package beats an A package.
- The same page says files under html_ui and ModelBehaviorDefs override only when the package lists them as globally overridden files.

What contradicts or qualifies them:
- Developer Mode's Package Reorder Tool page (https://docs.flightsimulator.com/msfs2024/retail/devmode/menus/tools/, read 2026-10-18) says priority comes from a priority and bucket generated from the hint, that the list mounts from lowest to highest priority, that reordering sets the hint of every package it moves to CUSTOM, that some packages are locked, that reordering writes an ordering file which Reset Order deletes, and that packages with the same priority and bucket mount in VFS order, which it calls not guaranteed and subject to change.
  So "alphabetical within a hint" is documented on one page and called not guaranteed on another; our machine shows alphabetical (below).
  On NTFS a folder listing is itself alphabetical, so no run on Windows can tell "alphabetical" from "folder listing order" (inference).
- A Navigraph staff reply (forum.navigraph.com, 2026-06-24) says that since SU3 the sim loads a package with no hint at the end (unverified, forum).
  Our measurement disagrees: p10's packages with an empty hint mounted long before the Baron's CUSTOM_SIMOBJECTS_PATCH package (measured on MSFS 2024, 2026-10-04, record/areas/aircraft/log.md, "2026-10-04: A Community package of ours adds a seat view anywhere in the aircraft...").
- html_ui without a global override list: FS Copilot's package lists none and its VCockpit.js loads in every panel (measured on MSFS 2024, 2026-08-30, FS Copilot fork, record/pointer-forwarding/docs/build/log.md, "2026-08-30 - The prototype module works end to end in the simulator"; restated in record/learn/foundations/02-01-installs-and-packages.md).
  Whether PANEL_PATCH is what makes it work stays unverified, as 02-01 says.

Which wins, measured: of aaa-crosscheck-camera-test and zzz-crosscheck-camera-test, both CUSTOM_SIMOBJECTS_PATCH, around bksq-aircraft-baronpro in the same group, the sim mounted aaa, then bksq, then zzz, and zzz's cameras.cfg replaced the others whole (measured on MSFS 2024, 2026-10-04, aircraft log, same entry).
So the last mounted wins.

Group order, read on our machine from the sim's report %APPDATA%\Microsoft Flight Simulator 2024\AsoboReport-OldCrashes\AsoboReport-Crash-4286222303.txt (BuildVersion="1.9.18.0", 2026-10-16), section [FlightSimulator_Packages], 235 Community and Marketplace packages, base packages not listed, each Community package's hint read from its manifest.json:
  GENERIC_AIRPORT_PATCH; CUSTOM_NAVDATA; CUSTOM_NAVDATA_PATCH; MISC; then one group holding absent hints, "" and NONE, in one alphabetical run from 29palms-ktnp-airport-msfs2024 to winwing-wwtwasm (crosscheck-p08-module 59th, fsc-editor-link 69th, navigraph-academy-2024 with NONE 87th); UI_PATCH; PANEL_PATCH (fscopilot-bridge alone, 121st); CUSTOM_INSTRUMENT; SIMOBJECTS_PATCH; CUSTOM_SIMOBJECTS; CUSTOM_SIMOBJECTS_PATCH; CUSTOM_MODELLIB_PATCH; CUSTOM_AIRPORT; CUSTOM_AIRPORT_LIFE; POI_PATCH.
  Marketplace packages, whose hints we couldn't read, sit between some of these groups.
  Within the unset group, its 17 Marketplace packages come first, alphabetical, then its 69 Community packages, alphabetical, so the source may order packages within a hint too (unverified).
  The aircraft log read the same ordering from AsoboReport-RunningSession.txt on 2026-10-04, and its measured winner matched the report's order within one group; that the report's list is the mount order for every group is unverified.
  Base packages such as asobo-vcockpits-core, hint INSTRUMENT, aren't in the report; FS Copilot's PANEL_PATCH copy beats the base copy (measured, above).
  Every name in the report is lowercase, so how a capital letter sorts (YourControls) is unverified.

Allowed hint values (documented, Package Tool XML Properties, https://docs.flightsimulator.com/msfs2024/flighting/sdk-tools/package-tool/package-tool-xml-properties/, read 2026-10-18):
- The table lists 64 hints alphabetically, with no mount order, and says third parties should use only those it flags for them.
- Flagged for third parties, among others: PANEL_PATCH (overrides PANEL packages), CUSTOM_INSTRUMENT, CUSTOM_INSTRUMENT_PATCH, UI PATCH (spelled with a space in the table; manifests use UI_PATCH), CUSTOM_SIMOBJECTS, CUSTOM_SIMOBJECTS_PATCH, SIMOBJECTS_PATCH, and the airport, scenery, library, navdata, and POI families.
- Not for third parties: INSTRUMENT, PANEL, UI, MISC, SIMOBJECTS, and INVALID, which the table calls the default for a package with no hint.
- NONE isn't in the table, though navigraph-academy-2024 uses it, and it mounts with the unset group (read).
- The table's flags on GENERIC_TEXTURELIB and GENERIC_TEXTURELIB_PATCH, and on INSTRUMENT_PATCH, contradict its own descriptions, so they may be swapped (unverified).
- The Project Inspector page lists the same hints by display name, such as "Panel patch" (https://docs.flightsimulator.com/msfs2024/html/2_DevMode/Project_Editor/The_Project_Inspector.htm).
- Hints in use on our machine (read): base install packages use MISC 46, MISSION 34, INSTRUMENT 22, SIMOBJECTS 3, INPUT 2, "" 2, and one each of GENERIC_TEXTURELIB, CUSTOM_INSTRUMENT, GENERIC_AIRPORT, SERVICES, and TRAVEL_BOOK; asobo-vcockpits-core is INSTRUMENT and fs-base-ui is MISC.

Its layout.json lists the path in lowercase, html_ui/pages/vcockpit/core/vcockpit.js.
- YourControls: folder YourControls; its 2024 manifest.json has no package_order_hint field at all, and its layout.json lists html_ui/Pages/VCockpit/Core/VCockpit.js and its modules/YourControlsGauge.wasm (read in YourControls/yourcontrols, main branch, scripts/build-include/2024/YourControls/, fetched 2026-10-18). FS Copilot's installer deletes a folder by that name (read in the FS Copilot fork, FsCopilot/Installer.cs, YcPackage).
- The FS Copilot fork's prototype: folder fscpp-bridge, PANEL_PATCH (read in its record/pointer-forwarding/module/tools/build.mjs). Its build refused to install beside fscopilot-bridge and printed a rename to fscopilot-bridge.off; a renamed folder inside Community is most likely a second package that still mounts (record/areas/install/results/2026-10-18-windows-and-msfs-facts.txt, F5, unverified), and "fscopilot-bridge.off" sorts before "fscpp-bridge", so the prototype would have won anyway (inference).
- Working Title: no workingtitle-instruments-* package in our install holds Pages\VCockpit\Core\ (read); only asobo-vcockpits-core does.
- Community scan on our machine (read 2026-10-18): only fscopilot-bridge lists pages/vcockpit/core/vcockpit.js; fnx-aircraft-320 puts three .glb colliders in that folder but no VCockpit.js. No Community package lists BlurPage's two paths.
- FlyByWire: not checked; flybywire-externaltools-simbridge in our Community lists no such path (read). Whether FlyByWire's aircraft packages override it is unverified.

What our record says about load-order conflicts:
- Two VCockpit.js overrides give "silently one or the other" (FS Copilot fork, record/pointer-forwarding/docs/10-module.md, "The conflict, and why the build refuses"); restated in 06-02, which also notes a pilot can likely run only one of Crosscheck, FS Copilot, and YourControls at a time (unverified there).

- FS Copilot profiles' captures, fsc/profiles/sim-sources/vcockpit02-displayunits/ and vcockpit12-efba220-1/, came through the inspector with FS Copilot installed, so they hold FS Copilot's copy (record/learn/foundations/06-02, "Traps").

- BlurPage: our p10 build read it from fs-base-ui\cookedcomps on disk, found through Steam's libraryfolders.vdf (read in experiments/areas/interface/menu/build.mjs, stockDir), because an XHR for coui://cookedcomps/ errored and the inspector listed no cookedcomps among mainUi's resources (measured on MSFS 2024, 2026-10-06, record/areas/interface/log.md, "2026-10-06: Our copy of BlurPage brings our script into the menu from the first screen, and from there it runs the whole join to Ready to fly").

Telling whether a sim update changed either file:

- A check that needs no sim: on a machine with the sim installed, hash the three files and compare with the hashes the build recorded for the release (the values above are the 1.9.18.0 ones).

Q3. FSPACKAGETOOL
======================================================================

What it is (read 2026-10-18 in the strings of <SDK>\Tools\bin\fspackagetool.exe, 75,264 bytes, SHA-256 EDA75A7D187FB45EDE71B59DD3189E614880F44642294600AA1AEBDD781A6F51, identical in SDK 1.7.3 and 1.8.1):
- Its usage text calls it fspackagetool v1.0 and says "you need to have Microsoft Flight Simulator 2024 installed" to run it.
- It finds the sim three ways: a path in fspackagetool_overrideExePath.txt beside it (empty in both SDKs here), the Store app Microsoft.Limitless_8wekyb3d8bbwe!App through the Application Activation Manager, or Steam's InstallPath from SOFTWARE\Valve\Steam, running steam.exe with -noverifyfiles -silent -nosplash -applaunch 2537590.
- It passes the build as the sim's own arguments (BuildAssetPackages, ExportForMarketplace, Mirror, Force, CheckOutputTimestamps, UsePause, LauncherPID, ModelBehaviorDefs), attaches to FlightSimulator2024.exe, and waits for it to finish.
- Options: -outputdir, -tempdir, -marketplace, -rebuild, -mirroring, -forcesteam, -outputtoseparateconsole, -nopause; the docs list the same and say the Store version builds unless -forcesteam is given (documented, https://docs.flightsimulator.com/msfs2024/html/8_SDK_Tools/Package_Tool/Package_Tool.htm).
- SDK 1.8.x's release notes list a fix for fspackagetool always running in community mode (documented, flighting SDK release notes, https://docs.flightsimulator.com/msfs2024/flighting/introduction/sdk-release-notes/).

So, on a machine with no sim, such as a GitHub-hosted Windows runner, it can't build anything: it has no FlightSimulator2024.exe to start.
Putting MSFS 2024 on a hosted runner would need a licensed Steam or Store sign-in and the game's install on each run (unverified; nobody has tried).
A self-hosted runner on a PC with the sim could run it, only while the sim is closed: with the sim running it hangs rather than failing (measured, fsc-editor, docs/sim-vars/build/v1-log.md, "2026-08-23 — The module becomes a sub-project, and fspackagetool cannot run with the sim open").
fsc-editor also wrote that the SDK has no unattended install; cargo-msfs unpacked the SDK without running its installer (measured 2026-10-08, record/areas/architecture/log.md, "2026-10-08: A standalone module built from Rust with cargo-msfs..."), which gives a runner fspackagetool.exe but not the sim it needs.

What doesn't need it:
- A Copy-only package (files, plus a manifest.json and layout.json our script writes) loads: p08's module, banner, and EFB packages (measured 2026-10-08 to 2026-10-09, architecture log), and the FS Copilot fork's prototype (FS Copilot fork, record/pointer-forwarding/docs/10-module.md, "Building").
- What does: the figure's SimObject model, which fspackagetool compiles (below), and an in-game panel's .spb, which p05 got from the Project Editor (read in experiments/areas/architecture/flight/build.mjs).
- Whether the sim spawns a SimObject from an uncompiled glTF in a Copy-only package is unverified; packaging the figure's source files with a Copy asset group and spawning it would settle it.

What our avatars log says (record/areas/avatars/log.md, "2026-10-03: A skinned stick took the sim down in an in-sim build, and a crashed sim held fspackagetool until it was closed", measured on MSFS 2024, 2026-10-03):
- Build and Mount of a skinned model in the Project Editor took the sim down; the build had copied the model's XML and never wrote its glTF or buffer.
- With the sim closed, fspackagetool failed twice after 121s with an empty _RPTErrors.xml.
- Something of the crashed sim, which the build's check for FlightSimulator2024.exe in the process list didn't catch, was still running; once the pilot closed it, the telescoping model built in 16s. Which process it was is unknown.

cargo-msfs (read in navigraph/cargo-msfs, tag v1.1.0, commit 5d3718d, %USERPROFILE%\.cargo\git\checkouts\cargo-msfs-<hash>\5d3718d\src\sdk.rs and src\main.rs; installed through cargo install --git, per %USERPROFILE%\.cargo\.crates2.json):
- get_latest_sdk_release fetches https://sdk.flightsimulator.com/msfs2024/files/sdk.json and takes game_versions.first().
- install_latest_sdk deletes %APPDATA%\cargo-msfs\data\msfs2024 first, downloads that entry's downloads_menu["SDK Installer (Core)"].value relative to https://sdk.flightsimulator.com/msfs2024/files/, opens the zip, reads its .msi and its external .cab files with the msi and cab crates, and writes every file under ".\MSFS 2024 SDK\" into the folder; it never runs the MSI, and the same code runs on Linux, which its Dockerfile does.
- It writes version.txt with release_notes.first() before extracting.
- There's no version argument: install, update, and info all take the first entry.
- Install refuses when version.txt exists; update reinstalls when version.txt's trimmed text differs from the latest version string.
- Navigraph ships a GitHub Action, action.yml, that runs cargo-msfs from a container image inside a workflow (read).

What a newer SDK changes (read 2026-10-18, comparing SDK 1.7.3 with 1.8.1 file by file):
- WASM\include: 8 of 153 headers changed. New functions fsVfxSpawnInWorld_EX1 and fsVfxSetWorldPosition_EX1, a new enum eFsWorldReference, new key events such as KEY_ADI_SYSTEM_TOGGLE and KEY_ENGINE_SPRAY_BAR_ON, default arguments moved behind a __MSFS_DEFAULT_PARAM__ macro, and six enum entries removed from Legacy\gauges.h.
  The release notes list the same VFX additions (documented, flighting SDK release notes, 1.8.1).
- SimConnect SDK\include\SimConnect.h: one line, SIMCONNECT_DATA_WAYPOINT's Flags from unsigned long to unsigned int. Both are 32 bits on Windows and wasm32; unsigned long is 64 bits on 64-bit Linux, so bindgen on a Linux host would have read the old header differently (inference).
- SimConnect.dll, SimConnect.lib, SimConnect_debug.lib, and the managed DLL changed; none carries a version resource.
- WASM\wasi-sysroot: 410 files, unchanged.
- WASM\WasmVersions\MSFS_WasmVersions.a: 3,830 bytes in both, two constants changed (2 to 3, and 1 to 2); it exports GetSimConnectVersion and GetExtensionVersion.
  The flighting docs say this library tells the sim which API versions a module was built with, so that older modules keep behaving as built, and that a Rust pipeline must link it (documented, https://docs.flightsimulator.com/msfs2024/flighting/programming-apis/wasm/webassembly/, "API Version Control"; the retail tree has no such section).
  Our Rust module ran both with it and without it, and the sim refused it when Rust's linker brought along the library's StackSizesSection (measured on MSFS 2024, 2026-10-08, architecture log, same entry).

Newer SDK on an older sim:
- WASM: our module built by cargo-msfs against SDK 1.8.1, which sdk.json pairs with sim 1.9, ran on sim 1.8.16 (measured, 2026-10-08, architecture log; the sim's report reads BuildVersion="1.8.16.0" on 2026-10-13, read). It called no function added in 1.8.1.
  A module importing a function the running sim doesn't have, such as an _EX1 call on an older sim, is unverified; a module importing one missing function, watched in the WASM Debug window, would settle it.
  The docs cover older modules on newer sims only.
- SimConnect: a client built on a newer SimConnect client DLL than the server typically gets SIMCONNECT_EXCEPTION_VERSION_MISMATCH, exception index 4 (documented, https://docs.flightsimulator.com/msfs2024/html/6_Programming_APIs/SimConnect/API_Reference/General/SimConnect_Open.htm).

  Whether SDK 1.8.1's SimConnect.dll meets a mismatch on a 1.8.x sim is unverified; one connect from a client on 1.8.1's DLL to a 1.8.x sim would settle it, which needs a sim on the older release.
