## 1. RFC 9443, Multiplexing Scheme Updates for QUIC
Source: https://www.rfc-editor.org/rfc/rfc9443.txt. Standards Track, July 2023; updates RFC 5764 and RFC 7983.

**Motivation [DOC, Abstract and §1]**
- RFC 7983 let one receiving port carry DTLS, STUN, SRTP/SRTCP, ZRTP, and TURN channel packets.
- RFC 9443 extends that "to also allow QUIC packets to be multiplexed on a single receiving socket."
- The use cases it names:
  - WebRTC peer-to-peer QUIC: the W3C P2P-QUIC report and Chrome 73's RTCQuicTransport origin trial. There, "SRTP/SRTCP [RFC3550], STUN, TURN, DTLS, and QUIC need to be multiplexed on the same port."
  - RTP over QUIC used peer to peer: "STUN, TURN, and QUIC need to be multiplexed on the same port."

**First-byte ranges [DOC, §3, new Figure 3]**

| First byte | Protocol |
| --- | --- |
| 0–3 | STUN |
| 4–15 | dropped |
| 16–19 | ZRTP |
| 20–63 | DTLS |
| 64–79 | TURN ChannelData if the packet comes from a responding TURN server's source IP and port, otherwise QUIC |
| 80–127 | QUIC |
| 128–191 | RTP/RTCP |
| 192–255 | QUIC |

Any other value "MUST be dropped."

**Why the 64–79 overlap is safe [DOC, §2]**
- TURN channels carry "a 4-byte prefix instead of the standard 36-byte STUN overhead."
- A QUIC short-header first byte can fall anywhere in 64–127, which overlaps TURN's 64–79.
- The RFC resolves this by source address: "a packet with a first octet of 64 to 127 can be unambiguously demultiplexed as QUIC" when it doesn't come from the TURN server.

**QUIC bit and greasing [DOC, §1 and §3]**
- The scheme is "compatible with QUIC version 2" but "not compatible with QUIC bit greasing [RFC9287]".
- So "endpoints that wish to use multiplexing on their socket MUST NOT send the grease_quic_bit transport parameter."
- Greasing would break the ranges [INFERENCE from RFC 9000 §17 header formats]. With the fixed bit cleared, a short header lands in 0–63 (the STUN, ZRTP, and DTLS ranges) and a long header in 128–191 (the RTP range).
- RFC 9287 §3.1 allows greasing only after receiving the peer's parameter, or with a NEW_TOKEN less than 7 days old from a server that advertised it [DOC].

**quinn's default [SRC, quinn-proto-0.11.19]**
- `EndpointConfig::new` sets `grease_quic_bit: true` (config/mod.rs).
- connection/packet_builder.rs then flips the bit at random: `if conn.peer_params.grease_quic_bit && conn.rng.random() { buffer[..] ^= FIXED_BIT; }`.
- Both peers must call `EndpointConfig::grease_quic_bit(false)`.

**Does it describe QUIC with ICE, STUN, and TURN on one 5-tuple? [DOC]**
- It speaks of "the same port" and "a single receiving socket," with traffic from the TURN server told apart by remote address. In effect that is one local socket serving several 5-tuples.
- The text never mentions ICE, and never describes QUIC carried inside TURN.
- For option C [INFERENCE]: QUIC on the TURN path arrives from the TURN server wrapped in ChannelData (64–79) or a Data indication (0–3). The TURN client unwraps it before quinn sees it.

## 2. IETF work combining QUIC with ICE or NAT traversal
Statuses are from the datatracker API, read 2026-10-10.

**draft-seemann-quic-nat-traversal-03, "Using QUIC to traverse NATs"** [DOC]
- Seemann and Kinnear (Apple), 8 Oct 2026. Individual submission with no WG state; draft-ietf-quic-nat-traversal returns 404, so there is no adopted successor.
- Revisions: -00 2023-07-10, -01 2023-10-23, -02 2024-03-04, -03 2026-10-08. Presented to the quic and avtcore WGs at IETF 117.
- Mechanism:
  - It starts from an already established proxied QUIC connection.
  - The server advertises its candidates in ALTERNATIVE_ADDRESS frames (draft-munizaga-quic-alternative-server-address-02).
  - The client pairs candidates using RFC 8445's pairing logic and asks for an attempt with PUNCH_REQUEST, spending a PUNCH_GRANT.
  - Both sides send PATH_CHALLENGE probes using "punching connection IDs" and report the result with PUNCH_DONE.
  - The connection then migrates to the validated path. Multipath is optional, using reserved Path ID 0xffffffff.
  - Gathering candidates is out of scope (§5.1), and amplification mitigation is still a TODO (§6.4).
- Relation to ICE: it "borrows address candidate pairing concepts from ... ICE ... but does not use the ICE protocol." It replaces ICE's STUN checks with probing inside QUIC.
- §3 describes option C as the baseline:
  - "When an external signaling channel is used, the QUIC connection is established after the two ICE agents have agreed on a candidate pair. This mode doesn't require any modification to existing QUIC stacks."
  - "QUIC and ICE need to use the same UDP socket ... the QUIC bit cannot be greased."

**draft-bruynooghe-n0-quic-nat-traversal-00** [DOC]
- Informational, 6 Jul 2026. It describes how noq does NAT traversal for iroh, "including all current bugs."
- It is based on Seemann's -02 "with heavy modifications," using ADD_ADDRESS, REMOVE_ADDRESS, and REACH_OUT frames.
- Its probes are PATH_CHALLENGE packets "not padded to 1200 bytes," so they don't validate the path. After a success the client opens a multipath path and validates it.
- Probes back off on the normal PTO and are abandoned after 30s.
- It admits sending probes on the active connection ID "in clear violation of Section 9.5" of RFC 9000.
- Candidates come from QUIC Address Discovery over a separate connection. To the QUIC stack, the relay path "looks like a normal IP path that uses IPv6 Unique Local Addresses."

**draft-ietf-quic-address-discovery-01** [DOC]
- QUIC WG document. -00 was adopted 2025-03-03, replacing draft-seemann-quic-address-discovery. It expired 2025-09-04, and -01 was posted 2026-08-15.
- Mechanism:
  - The `address_discovery` transport parameter (0x9f81a176) takes 0, 1, or 2.
  - OBSERVED_ADDRESS frames (0x9f81a6–a7) carry sequence numbers. They are probing frames and are sent on every new path.
- Its §1 motivation ends: "If QUIC traffic doesn't need to be demultiplexed from STUN traffic, implementations can enable QUIC bit greasing."
- It replaces STUN for learning a server-reflexive address, and needs a cooperating QUIC server.

**draft-ietf-quic-multipath-21** [DOC]
- Dated 17 Mar 2026. It is not an RFC yet. The IESG state has been "RFC Ed Queue" since 2026-03-19, and the RFC Editor was on its second edit as of 2026-10-07.
- It "only enables clients to open a new path."
- It "does not specify address discovery or management, nor how applications using QUIC schedule traffic over multiple paths."
- It is the one-connection, many-paths alternative to option C's two connections.
- Upstream quinn doesn't have it: issue #224 "Implement support for multipath" is still open, last updated 2026-02-04 [SRC]. noq implements it.

**draft-thatcher-p2p-quic-00, "P2P QUIC"** [DOC]
- July 2023; expired January 2024. "describes how to combine ICE and QUIC to do p2p QUIC". This is the closest to option C.
- "QUIC packets MUST be sent using the ICE selected candidate pair."
- It demultiplexes ICE from QUIC by the STUN magic cookie.
- §11: "ACKed QUIC PING frames MAY be treated the same as a succesful ICE check" (sic).
- §12: "Network migration SHOULD be done using ICE, not QUIC." QUIC should still change behavior, such as congestion control, "as if it had done a network migration," but "SHOULD NOT change the connection ID."
- §8: QUIC multipath "SHOULD NOT be used unless it is known that one of the peers is a server."

**draft-perkins-quic-p2p-mux-00** [DOC]
- March 2019; expired. An outline:
  - gather candidates per RFC 8445 for a single QUIC component;
  - exchange them either out of band or embedded in QUIC;
  - run the connectivity checks with STUN;
  - open QUIC on the chosen pair, possibly as a simultaneous open;
  - demultiplex per draft-aboba-avtcore-quic-multiplexing, which became RFC 9443.

**MASQUE** [DOC]
- RFC 9298, "Proxying UDP in HTTP" (CONNECT-UDP), proxies to one fixed target.
- draft-ietf-masque-connect-udp-listen-16, "Proxying Bound UDP in HTTP":
  - It is in the RFC Editor queue; IANA reached RFC-Ed-Ack on 2026-08-31.
  - It exists because ICE needs to send to several hosts from one address.
  - It adds `Connect-UDP-Bind` and `Proxy-Public-Address`.
  - Its security section says TURN "can be run over this mechanism."
  - For option C it would be a relayed candidate reached over HTTP/3 or HTTP/2 instead of TURN [INFERENCE].
- draft-seemann-masque-connect-udp-rendezvous-00 (2026-08-16, individual) relays between two clients of the same proxy. "No public UDP address is allocated." That is closer to the iroh-relay and DERP model.
- I didn't examine draft-ietf-masque-quic-proxy-09, draft-li-quic-nat-optimization-00, or draft-duke-quic-natsupp-03.

## 3. RTP over QUIC and its SDP
**draft-ietf-avtcore-rtp-over-quic-14 (RoQ)** [DOC]
- Status: posted 2025-03-21, WG Last Call since 2025-07-03, expired 2025-09-21.
- [SRC, a text search of -14]: it mentions STUN, TURN, RFC 9443, and RFC 7983 zero times, and ICE twice.
- §3.3, Table 1 marks Topo-PtP-Relay "yes" with Note-NAT: "Not supported, because QUIC [RFC9000] does not support NAT traversal."
- §13.2 lists as future work "Guidance for using RoQ with QUIC NAT traversal solutions. This could use ... (ICE) [RFC8445] or other NAT traversal solutions."
- Its term "peer" "does not have anything to do with 'peer-to-peer' operation."
- So RoQ defines no ICE use, no multiplexing, and no peer-to-peer mode.

**draft-ietf-avtcore-sdp-roq-00** [DOC]
- A WG document from October 2025. It replaced draft-dawkins-avtcore-sdp-rtp-quic and draft-dawkins-avtcore-sdp-roq, and expired 2026-04-14.
- §6.4 assumes that endpoints needing NAT traversal "will perform ICE procedures as described in [RFC8445]." Because QUIC validates the peer's address, "an ICE agent will have already performed ICE candidate pair connectivity checking before a QUIC connection can be opened."
- It lists liveness checks at several layers:
  - QUIC PING frames;
  - ICE keepalives (RFC 5245 §10, RFC 6263);
  - consent freshness (RFC 7675);
  - RTCP.
- It concludes that consent freshness "also serves the ICE keepalive function, so ICE keepalives are no longer necessary."
- An editors' note says other NAT traversal methods are possible.

**Earlier and related SDP drafts** [DOC]
- draft-dawkins-avtcore-sdp-rtp-quic-00 (January 2022) said peer-to-peer RoQ "likely would require extensions to the QUIC protocol for NAT traversal, at a bare minimum."
- draft-thatcher §14 defines `UDP/QUIC` in SDP with the standard ICE attributes plus `a=setup` and `a=fingerprint`.

    | `trustUDPAddrDuration` | 6.5s |
    | `goodEnoughLatency` | 5ms |

  - `endpoint.go`: `addrForSendLocked` sends to both the UDP address and DERP once trust in the best UDP address expires. WireGuard addresses the peer by `fakeWGAddr`, which is the same idea as option C's virtual address.
  - `endpoint.go` also probes how long UDP mappings live, at cliffs of 10s, 30s, and 60s.
- Peer Relays (beta 2025-10-29) [DOC]: each relay uses "a single UDP port," and clients try a direct path, then a peer relay, then DERP.

**Differences from option C** [INFERENCE from the sources above]

| | Relay protocol | Path probing | Connections |
| --- | --- | --- | --- |
| iroh 1.x | WebSocket over HTTPS (TCP) | in-QUIC PATH_CHALLENGE (QNT) | one QUIC connection; the relay and each direct address are multipath paths with their own congestion control and RTT |
| Tailscale | DERP over HTTP(S)/TCP; Peer Relays on UDP | disco ping and pong | one WireGuard session; magicsock switches the path underneath; WireGuard has no congestion control of its own |

## 6. Measured hole-punching success
- **libp2p DCUtR**, Trautwein et al., IMC '26, arXiv:2604.12484 (v1 2026-04-14) [MEASURED-BY-OTHERS]
  - 4.4M+ attempts from 85,000+ networks in 167 countries.
  - Success "70% ± 7.1%," conditional on the relay reservation and address discovery succeeding first.
  - TCP and QUIC both ~70%.
  - 97.6% of successes came on the first attempt.
  - The paper cites carrier-grade NATs using endpoint-dependent mapping "in 40% of cases as of 2016" (Richter et al.).
- **ProbeLab, "Can libp2p punch through NATs?"** (2026-08-03), via the fetch tool's summary [MEASURED-BY-OTHERS]
  - Port-restricted cone: 82.9% (3,042 of 3,669).
  - Symmetric: 39.7% (213 of 536).
  - About 36% of NAT'd peers never got a relay reservation.
  - Confirmed symmetric NATs were 3.9% of 43,684 classified peers.
- **Tailscale, NAT traversal improvements part 1** (2025-10-15) [MEASURED-BY-OTHERS]: "Internal metrics have indicated success rates for direct NAT traversal well north of 90% in typical conditions." The 2020 post's "over 90%" is an estimate, not a measurement.
- **iroh docs** (concepts/relay) [DOC]: "Anecdotal evidence points to the holepunching rate being around 90%." A formal collection is in progress.
- **callstats.io via webrtcHacks** (2016-04-08; data from January 2015 to February 2016) [MEASURED-BY-OTHERS]: "22% of the conferences need some kind of TURN relay server," and "About 9% of the conferences required TCP."
- **Ford, Srisuresh, and Kegel**, bford.info/pub/net/p2pnat, via the fetch tool's summary [MEASURED-BY-OTHERS]:
  - UDP hole punching worked with 82% of NATs (310 of 380 data points).
  - TCP: 64% (184 of 286).
  - The sample "do[es] not constitute a random sample."
- **Halkes and Pouwelse 2011**, quoted in the DCUtR paper [MEASURED-BY-OTHERS]: "approximately 64% of all peers are behind a NAT box or firewall which should allow hole punching to work, and more than 80% of hole punching attempts between these peers succeed." The primary source was bot-blocked.

## 7. Known pitfalls
- **Greasing.** quinn advertises `grease_quic_bit` by default and greases about half its packets once the peer has advertised it. Both sides must turn it off (§1 above) [SRC].
- **MTU.**
  - RFC 9000 §14 requires paths to carry at least 1,200 bytes of UDP payload. At a 1,280-byte IP MTU, the payload ceiling is 1,232 bytes on IPv6 and 1,252 on IPv4 [DOC].
  - TURN overhead: ChannelData adds 4 bytes, padded only over TCP or TLS (RFC 8656 §12.5). A Send indication adds "36-byte" overhead (RFC 9443 §2) [DOC].
  - At the IPv6 minimum MTU, ChannelData leaves 1,228 bytes, which fits. A Send indication leaves 1,196 bytes, or 1,184 with an IPv6 peer address, which is too small for a 1,200-byte Initial. So bind the channel before the QUIC handshake [INFERENCE].
  - RFC 8656 §3.7 says to assume a 1,280-byte path MTU, recommends ChannelData, and suggests ≤500 bytes of payload as a rule of thumb. §3.6: no end-to-end fragmentation, and the relay may reset ECN [DOC].
- **quinn MTU discovery with a custom socket** [SRC, quinn-0.11.12]
  - `AsyncUdpSocket::may_fragment()` defaults to true, and `Endpoint::new_with_abstract_socket` sets `allow_mtud = !socket.may_fragment()`. A custom socket therefore turns off MTU discovery for the whole endpoint unless it overrides this.
  - quinn-udp's Windows socket sets `IP_DONTFRAGMENT` and `IPV6_DONTFRAG` and returns false.
  - Per connection, `TransportConfig::{initial_mtu, min_mtu, mtu_discovery_config}` are available.
- **Path changes under a stable virtual address.**
  - quinn-proto 0.11.19 drops a client's packets from a new remote ("discarding packet from unrecognized peer") [SRC].
  - RFC 9000 §9.4 requires resetting congestion control and RTT after an address change; a virtual address never triggers that [DOC].
  - quinn 0.11.12's `Connection` has no method to reset congestion state. Ralith in #2016: "A method to return the congestion controller to the initial state doesn't exist" [SRC].
  - `is` may re-nominate a pair at any time, so option C must decide what to do when that happens [INFERENCE].
- **Keepalive and consent.**
  - RFC 7675 §5.1: consent expires after 30s; checks go out every 5s by default (randomized to 4–6s), and never less than 4s apart [DOC].
  - RFC 8445 §11: send a keepalive if nothing was sent for Tr = 15s, never less than 15s, and "Agents MUST by default use STUN keepalives." Any packet resets the timer [DOC].
  - quinn defaults to `keep_alive_interval: None` and `max_idle_timeout` 30s, citing RFC 9308 [SRC].
- **TURN state** [DOC, RFC 8656]
  - An allocation lasts 600s by default and is refreshed only by Refresh: "sending data to a peer does not refresh an allocation."
  - Permissions last 300s; channel bindings last 10 minutes.
  - ChannelData received by the server "MUST NOT refresh either the channel binding or the permission."
- **Cloudflare Realtime TURN** [DOC, FAQ]
  - Relayed addresses are IPv4 only: it "will issue IPv4 addresses only."
  - It doesn't implement RFC 6062 (TCP relaying).
  - It "denies CreatePermission or ChannelBind requests if private IP ranges" are used.
  - Credentials last at most 48 hours.
  - Maintenance or anycast changes can disrupt an allocation, so "ICE restart ... support by clients is highly recommended."
  - The documentation doesn't address ChannelData, MTU, or payloads other than WebRTC's.
- **NAT mapping timeouts.**
  - RFC 4787 REQ-5: a mapping MUST NOT expire in less than 2 minutes, and 5 minutes or more is recommended [DOC].
  - RFC 8085 §3.5: keepalives no more often than every 15s, though "a significant fraction" of middleboxes use shorter timeouts [DOC].
  - RFC 9308 §3.2, citing Hätönen 2010: state "can expire after just thirty seconds of inactivity" [MEASURED-BY-OTHERS].
  - Tailscale 2020: "a common value for UDP is 30 seconds." Carrier-grade NATs "typically employ short port timeouts and symmetric mapping" [DOC].
- **Windows.**
  - An ICMP port-unreachable makes the next `recvfrom` fail with `WSAECONNRESET` [DOC: Microsoft's recvfrom documentation].
  - quinn's receive loop ignores `ConnectionReset` [SRC: `quinn/src/endpoint.rs` at quinn-0.11.12].
  - quinn-udp 0.6.3 doesn't set `SIO_UDP_CONNRESET` [SRC].
  - noq-udp turns off both `SIO_UDP_CONNRESET` and `SIO_UDP_NETRESET`: "We never want to fail the recv path due to a failed send" [SRC, noq-udp/src/windows.rs; last commit to that file db9bf72ac4].
  - Option C's demultiplexer reads the shared socket itself, so it needs the same handling, because hole-punch probes go to closed ports [INFERENCE].
